# Личные уведомления

NotificationModule предоставляет inbox пользователя. Все маршруты требуют
существующую HttpOnly access cookie; изменения — разрешённый Origin. Ответы no-store.
Получатель всегда берётся из сессии, передать чужой userId нельзя.

- `GET /notifications?state=all|unread&limit=20&after=...` — `{ items, nextCursor }`.
  Лимит 1–100, порядок createdAt DESC, id DESC. Курсор привязан к пользователю и
  фильтру; неправильный курсор даёт 400. Это живой список: новые доставки и прочтение
  могут менять страницы. Периодически обновляйте первую страницу и счётчик.
- `GET /notifications/unread-count` — `{ count }`, включая недоступные старые ссылки.
- `PATCH /notifications/:id/read` — `{ id, readAt }`; повтор сохраняет первую дату.
  Чужое/отсутствующее/истёкшее уведомление даёт 404.
- `PATCH /notifications/read-all` — `{ count }` изменённых записей. Повтор даёт 0.
  Отмечаются уже доставленные записи на момент SQL-запроса; будущие доставки остаются непрочитанными.

Элемент содержит id, kind, title, body, actorId, createdAt, readAt, available,
и target `{ organizationId, projectId, taskId }` либо null. createdAt — время события
назначения, а не время отложенной доставки. Курсоры не являются разрешением доступа.
Polling на клиенте достаточен для этой версии; SSE/WebSocket не добавлены.

## Какие события создают уведомления

Существующая история TaskEvent остаётся источником. Событие CREATED с назначениями
или ASSIGNMENTS_CHANGED с added создаёт задания в NotificationJob SQL-триггером
в той же транзакции. Откат задачи/события откатывает очередь. Старые события при
миграции не воспроизводятся.

ASSIGNEE и RESPONSIBLE дают TASK_ASSIGNED, REVIEWER — TASK_REVIEW_REQUESTED.
Совмещение ASSIGNEE+RESPONSIBLE в одном событии даёт одно сообщение; назначение
ревьюера дополнительно даёт запрос ревью. Уникальный sourceKey — event ID +
recipient ID + notification kind. Самоназначение не создаёт сообщений. No-op
назначения не создают события/задания. Снятие и последующее новое назначение —
новое событие и новое уведомление. Смена статуса на REVIEW сама по себе не создаёт
запрос: запросом в этой версии служит назначение REVIEWER.

В снимке сохраняются ключ и название задачи, имя инициатора и краткая формулировка
назначения. Markdown, контакты и пароли не копируются. Приглашения в организацию,
добавление в проект и email-доставка не включены в этот этап. Все новые Notification
имеют emailStatus=DISABLED; почтовые сервисы не вызываются.

## Обработка и повторы

`NOTIFICATION_WORKER_ENABLED=true` по умолчанию. Фоновый обработчик внутри API
проверяет очередь раз в 5 секунд, до 25 заданий за проход. Реплики используют
`FOR UPDATE SKIP LOCKED`; внешних запросов внутри транзакции нет. В NODE_ENV=test
автоматический таймер отключён, интеграционные тесты вызывают обработчик явно.
Флаг false позволяет отдельно отключить обработку, сохраняя приём заданий.

Создание Notification и processedAt задания фиксируются одной транзакцией.
При падении процесса незавершённая транзакция откатывается, задание доступно снова.
Уникальный sourceKey Notification защищает даже повтор после сброса processedAt.
Ошибка отдельного задания откатывается до savepoint; attempts и availableAt
сохраняют повтор с задержкой 5 секунд, затем экспоненциально до часа. Остальные
задания продолжают обрабатываться. Нет необратимого удаления после N ошибок:
повторы продолжаются до истечения срока хранения. lastError содержит только
DELIVERY_FAILED, журнал не раскрывает SQL, payload или секреты.

Задание с удалённой задачей или потерянным явным членством получателя пропускается
и отмечается обработанным. Прошлые назначения не восстанавливаются после повторного
вступления. Выход worker при остановке API ждёт активную транзакцию, затем Prisma
закрывает соединения. Не запускайте старый API одновременно с новой миграцией/версией.

Для эксплуатации следите за количеством pending-заданий, возрастом самого старого
availableAt и ростом attempts/lastError. Readiness проверяет БД/Redis, а не задержку
уведомлений; успешный healthcheck не заменяет наблюдение за очередью.

## Приватность и хранение

Срок первой версии — 90 дней с момента события. Истёкшие сообщения сразу исключаются
из API. Worker удаляет Notification и NotificationJob ограниченными пачками до 200
строк каждой таблицы за проход; при остановленном worker физическая очистка ждёт
его запуска. Очередь хранит скалярные ссылки, чтобы удаление задачи не ломало обработку.

Чтение списка проверяет текущую доступность задачи в едином RepeatableRead-снимке:
членство в организации и проекте либо owner организации. После потери доступа или
удаления задачи пользователь видит только своё уведомление с общей надписью
«Задача недоступна», без названия/текста/actorId/ссылки. Его можно отметить прочитанным.
После восстановления доступа ранее доставленный снимок снова доступен до окончания
срока. Переход по target всегда дополнительно проверяется TaskModule.

## Поставка и проверки

Миграция `20261120000000_notification_outbox` добавляет очередь, sourceKey и индексы,
включая индексы для ограниченной очистки. Старые уведомления сохраняются, sourceKey
для них null. Перед новым API примените миграцию штатным migrator. Локальная рабочая
БД в ходе разработки не мигрируется автоматически.

Проверки: DTO/cursors, чужой inbox, пагинация и отметки, отсутствие self-уведомлений,
дедупликация совмещённых назначений, параллельные обработчики, возобновление новым
экземпляром worker после SQL-ошибки, полный откат при ошибке outbox, потеря доступа,
удаление задачи и 90-дневное истечение. Docker smoke test проверяет автоматическую
доставку таймером production API, кроме healthcheck. Запуск: `npm run test:domain`;
для Docker smoke передайте DOMAIN_API_IMAGE и DOMAIN_MIGRATION_IMAGE собранных образов.
