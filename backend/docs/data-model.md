# Модель данных таск-трекера

Схема: `prisma/schema.prisma`. Все доменные таблицы и enum находятся в PostgreSQL-схеме `app`; история Prisma-миграций — в `public`.

## Область реализации

Сейчас реализованы модели, связи, индексы, SQL-ограничения и интеграционная проверка. API пользователя, организаций и проектов описаны в [user-module.md](user-module.md), [organization-module.md](organization-module.md) и [project-module.md](project-module.md). Отправка почты, загрузка файлов, GitHub webhooks и LLM-интеграции пока не реализованы.

Существующие поля User `id/email/name/password/role/tokenVersion` сохранены для совместимости с текущим auth-кодом. `User.role` — существующая платформенная роль USER/ADMIN; она не является ролью внутри организации и не должна автоматически открывать чужие проекты.

## Пользователь

- `User`: email, имя, хеш пароля, время подтверждения email, аватар, телефон, описание, GitHub URL, IANA time zone и timestamps.
- `UserSocialLink`: произвольные ссылки с необязательной подписью и порядком.
- `UserWorkInterval`: день недели ISO (1–7) и локальные минуты начала/окончания (0–1440). Ночная смена задаётся двумя интервалами.
- «Работает сейчас» вычисляется по текущему времени, timezone и расписанию, с учётом DST. Это не признак online-присутствия. IANA timezone и URL нужно валидировать на уровне будущего DTO.
- `emailVerifiedAt = null` означает «не подтверждён». Проверка и отправка email пока не подключены; development-доступ не подменяет факт подтверждения. Перед production потребуется включить проверку, выдачу/погашение verification-токена и сброс подтверждения при смене email.
- Email уникален также без учёта регистра и внешних пробелов. Будущий API должен нормализовать адрес и при записи, и при поиске; уникальный индекс сам не нормализует findUnique.
- Общие организации/проекты профиля получаются пересечением членств. При выдаче нужно учитывать право посетителя видеть каждый проект; отдельная таблица «общих проектов» не нужна.

## Организации и owner

`OrganizationMember` связывает User и Organization. У организации один `ownerUserId`, который обязательно ссылается на её участника. Системная роль `owner` выводится из этой ссылки, не хранится редактируемой строкой OrganizationRole и всегда даёт все права организации и её проектов.

Владелец не зависит от roleId и переопределений проекта. Имя owner зарезервировано для пользовательских ролей. Изменить права или удалить системную роль невозможно через каталог обычных ролей.

Создавай организацию и её owner-членство в одной транзакции: внешний ключ владельца проверяется при commit. Например:

```ts
const organizationId = randomUUID();
await prisma.$transaction(async (tx) => {
  await tx.organization.create({
    data: { id: organizationId, name, slug, ownerUserId: userId },
  });
  await tx.organizationMember.create({
    data: { organizationId, userId },
  });
});
```

Передача владения — изменение `Organization.ownerUserId` на существующего участника в авторизованной транзакции. В каждый зафиксированный момент есть ровно один владелец. У бывшего owner остаётся его обычная roleId; если её нет, обычные права отсутствуют. Удалить владельца из организации до передачи владения не получится.

Удаление пользователя с членствами запрещено внешним ключом: сначала нужно передать владение и явно завершить членства. Это не мешает удалению самой организации с её зависимыми данными.

## Роли и доступ к проектам

**Текущее продуктовое решение:** роли пока только визуальные. У всех участников
организации одинаковые возможности, кроме защищённых действий owner. Доступ к
проекту требует членства, внутри проекта возможности равны; owner видит все проекты.
Ниже описан сохранённый задел схемы для будущих permissions, который сейчас не
применяется API. Текущие контракты: [organization-module.md](organization-module.md)
и [project-module.md](project-module.md).

- `OrganizationRole`: настраиваемое название, набор прав организации и базовых прав проектов.
- `OrganizationMember.roleId`: текущая организационная роль. NULL у обычного участника означает отсутствие грантов роли.
- `ProjectMember`: явное членство в проекте. `roleId = null` наследует текущую роль участника в организации; конкретный roleId выбирает другую роль из каталога той же организации.
- `ProjectRoleOverride`: разрешённые/запрещённые права конкретной роли в конкретном проекте.
- `ProjectMember.allowPermissions/denyPermissions`: исключения для конкретного участника.
- В массивы разрешений и запретов одной записи нельзя записать одно и то же право.

Порядок вычисления доступа будущим authorization-сервисом:

1. Owner организации получает все права, включая проекты без ProjectMember.
2. Для остальных нет ProjectMember — нет доступа к проекту.
3. Выбирается явная роль проекта либо текущая роль организации.
4. Берутся `OrganizationRole.projectPermissions`.
5. Применяются allow/deny из ProjectRoleOverride выбранной роли.
6. Применяются персональные allow/deny из ProjectMember.
7. Без итогового VIEW_PROJECT проект и его содержимое не выдаются, даже если другие гранты остались.

На каждом уровне сначала добавляются allow, потом убираются deny. Более конкретный уровень переопределяет менее конкретный. Отсутствие переопределения означает живое наследование: изменения организационной роли видны сразу. Не копируй roleId и весь набор прав при добавлении участника в проект.

Роль Fullstack в организации и Frontend в проекте — две записи каталога организации и явный ProjectMember.roleId. Отдельных копий ролей для проекта не требуется.

Нельзя удалить используемую обычную роль без переназначения участников, удаления её project overrides и обработки приглашений. Для этого нужны транзакции. Проверки прав API обязательны: внешние ключи изолируют связи, но не выполняют авторизацию запросов сами.

## Проекты, доска и задачи

`Project` принадлежит организации. Одна доска проекта представлена его задачами, сгруппированными по `TaskStatus`; отдельная сущность Board пока не нужна.

`TaskStatus` имеет настраиваемые имя, цвет, порядок и семантическую категорию BACKLOG/TODO/IN_PROGRESS/REVIEW/DONE/CANCELED. Стартовые колонки создаёт ProjectService вместе с проектом; миграция не создаёт демонстрационные проекты и статусы. Удаление занятого статуса требует переноса задач в другой статус того же проекта.

`Task` содержит UUID, номер внутри проекта, заголовок, Markdown, статус, необязательный тэг, автора, preview URL, срок, архивирование, timestamps и Decimal-позицию на доске. Сортировка: статус, position, id; при плотных позициях сервис может перебалансировать значения.

Внешний ключ задачи: `<Project.taskPrefix>-<Task.number>`, например `task-WEB-13`. Префикс уникален в организации, номер — в проекте; UUID остаётся глобальным техническим ID.

- При вставке задачи PostgreSQL атомарно увеличивает Project.lastTaskNumber и выдаёт номер. Поле number при Prisma create можно опустить.
- Значение 0 в Prisma — служебный default до BEFORE INSERT trigger; сохранённый номер всегда положительный.
- Номер нельзя сменить, задача не переносится в другой проект простым UPDATE. Префикс можно настроить до первой задачи; после выдачи номеров он фиксируется для стабильных ссылок.
- Удалённые номера не используются повторно; откат транзакции откатывает и выдачу номера. Разрывов между существующими задачами может быть сколько угодно.
- Не вычисляй номер через count/MAX и не инкрементируй счётчик второй раз в сервисе.

`TaskTag` задаёт имя, цвет и branchPrefix (feat/bug/hotfix). На этом этапе у задачи один необязательный тэг. Предложение имени ветки вычисляется как `<tag.branchPrefix>/<taskPrefix>-<number>`; без тэга можно использовать сам ключ задачи. Git-ref нужно проверять при создании ветки.

`TaskAssignment` допускает нескольких ответственных, исполнителей и ревьюеров, в том числе несколько функций одного участника. Назначать можно только ProjectMember того же проекта. Удаление членства снимает его назначения; историю действий следует сохранять отдельными событиями/уведомлениями.

`TaskAttachment` хранит метаданные изображения/файла и ключ внешнего хранилища. Файловых байтов в БД нет. Загрузка, проверка mime/размера, доступ к объектам и безопасный Markdown renderer относятся к будущему API/UI. previewUrl необязателен.

## GitHub

`ProjectRepository` позволяет прикрепить несколько репозиториев к проекту. `TaskBranch` связывает задачу с фактической веткой репозитория того же проекта; задача может затрагивать несколько репозиториев. Если ветка ещё не обнаружена, записи TaskBranch нет.

Репозиторий содержит публичные метаданные, не access token. Автопоиск веток, PR, webhooks, изменение статуса по merge и генерация коммитов пока не реализованы.

## Приглашения и уведомления

`OrganizationInvitation` содержит email, роль, автора, срок, hash случайного токена, отметки принятия/отзыва и принявшего пользователя. Owner через приглашение не назначается.

Одновременно допускается одно непринятое и неотозванное приглашение на email в организации без учёта регистра. Для повторной отправки истёкшее приглашение нужно явно отозвать/обновить. При принятии будущий сервис проверяет срок, совпадение email, hash токена и атомарно создаёт членство вместе с acceptedAt/acceptedById. Сохранённый hash не является JWT-сессией: JWT/refresh-состояние по-прежнему относится к Redis.

`Notification` — событие для inbox: получатель, автор, тип, задача/приглашение, текстовый снимок, время создания и прочтения. При удалении задачи или автора ссылки обнуляются, текст остаётся. При назначении нужно создавать событие в той же транзакции, что и TaskAssignment.

Email имеет состояние DISABLED по умолчанию. Поля доставки оставляют возможность последующего mail worker; очереди, ретраи и отправка сейчас отсутствуют. При работе с inbox также нужны проверка recipientId и безопасная обработка недоступных пользователю ссылок.

## Миграции и проверки

Миграция `20261113000000_task_tracker_domain` добавляет модели после исходной миграции, создавшей только схему app. Она не предназначена для базы с таблицами, созданными вручную через db push: перед применением нужно сверить историю и фактическую схему.

SQL дополнительно содержит проверки диапазонов/состояний, индексы email, отложенные FK и триггеры нумерации. Эти части Prisma schema не выражает полностью. Не заменяй применение миграций командой db push. При следующей миграции сохраняй пользовательский SQL. Новая миграция выполняется в транзакции.

Проверки из backend:

```sh
npm run prisma:validate
npm run lint
npm test -- --runInBand
npm run test:domain
```

test:domain собирает backend, создаёт отдельный PostgreSQL-контейнер с временным файловым хранилищем и случайным loopback-портом, применяет весь migration chain дважды и сверяет Prisma-schema с БД. Сценарии выполняются через настоящий Prisma Client с ограниченной ролью task_tracker_app. Тест не использует локальный .env или рабочую БД и удаляет только собственный контейнер. Нужны Docker, подходящая версия Node и локальный образ PostgreSQL из compose.yaml; автоматического скачивания нет.

Проверяются owner/передача владения, роли и границы организаций/проектов, параллельная нумерация, защита статусов/тэгов, назначения, ссылки на репозитории, приглашения, уведомления, каскады и изоляция migration/runtime-ролей.
