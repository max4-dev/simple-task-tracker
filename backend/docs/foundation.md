# Исправления основы backend

## Контракты

Роли остаются визуальными. Членство даёт доступ к организации/проекту, owner
организации сохраняет исключительные действия передачи владения и удаления.
Неиспользуемые permission-поля схемы не применяются API; новые модули не должны
интерпретировать roleId=null как запрет доступа.

Сохраняется одна активная сессия на пользователя. Новый вход с текущим паролем
заменяет предыдущий. Ключи Redis имеют формат
`session:v2:{userId}:tokenVersion:access|refresh`; в значениях только SHA-256
отпечатки токенов. При смене пароля удаляется старое поколение, а проверка
tokenVersion в PostgreSQL немедленно закрывает старые JWT даже при отказе Redis.
Запоздавший login/refresh не перезаписывает поколение нового пароля. Перед
установкой cookie сервис повторно проверяет текущую версию.

`POST /auth/register` возвращает 201 после создания аккаунта:

- `authenticated: true` и HttpOnly cookie — сессия открыта;
- `authenticated: false`, `code: SESSION_UNAVAILABLE` и очищенные cookie — аккаунт
  создан, но Redis не сохранил сессию. Клиент предлагает повторить **вход**, а не
  регистрацию. Отказ до создания аккаунта не возвращает этот результат.

Ответ содержит безопасный объект user (id/email/name), без JWT и пароля.
Login/refresh возвращают `authenticated: true` только при успешной сессии.
Ответы auth запрещено кешировать. Распределённая транзакция PostgreSQL+Redis не
имитируется; уже созданный аккаунт при сбое сессии не удаляется.

Ошибки HTTP имеют поля `statusCode`, `code`, `message`, `requestId`.
Для валидации message может быть массивом. Базовые коды: INVALID_REQUEST,
UNAUTHENTICATED, FORBIDDEN, NOT_FOUND, CONFLICT, RATE_LIMITED, SERVICE_UNAVAILABLE,
INTERNAL_ERROR. Сбой хранилища лимитов: RATE_LIMIT_UNAVAILABLE; сбой открытия
сессии при login: SESSION_UNAVAILABLE. UUID запроса создаётся сервером и доступен
также в X-Request-Id. Ошибки драйвера не попадают в ответ или лог; серверные ошибки
логируются как requestId/statusCode/code без URL, cookie, JWT и входного тела.

## Лимиты и прокси

Счётчики всех защищённых ThrottlerGuard-маршрутов хранятся в Redis, общие для
реплик. Lua выполняет учёт запросов и блокировку атомарно. При отказе счётчика
запрос отклоняется, а не пропускается без ограничения.

Смена пароля: 5 запросов/минуту на аутентифицированного пользователя и 20 на IP.
Считаются все попытки, включая успешные. Auth-маршруты сохраняют лимит 10/минуту
на маршрут и IP; удаление организации/проекта — 5. Лимиты не применяются к
обычному редактированию проектов и будущих карточек автоматически.

TRUSTED_PROXY_CIDRS — список IP/CIDR доверенных reverse proxy через запятую.
По умолчанию пустой: X-Forwarded-For игнорируется. Разрешены явные IPv4/IPv6-сети,
универсальные /0, true, число переходов и имена хостов не принимаются.
Укажите фактическую сеть своего proxy, который должен очищать/корректно дополнять
forwarding-заголовки. Не добавляйте сеть обычных клиентов. Compose передаёт
переменную API; пользовательский .env автоматически не изменяется.

## Приглашения и удаление роли

Новая миграция `20261119000000_invitation_role_history` добавляет обязательный
снимок roleName, заполняет его для существующих записей и разрешает nullable
roleId. CHECK разрешает отсутствие роли только у принятого/отозванного приглашения.
Внешний ключ роли остаётся в пределах организации.

Удаление роли проверяет членства, проектные переопределения и активные приглашения.
Истёкшие приглашения отзываются; завершённые отвязываются от роли в той же
транзакции. Их снимок названия сохраняется. Активное приглашение продолжает
блокировать удаление. Приём приглашения проверяет срок, состояние, роль и email
под общей блокировкой организации.

## Блокировки

После реализации доски проектные writers используют Organization FOR SHARE →
Project FOR UPDATE → проверка текущего доступа → запись. Изменения организации
(member/owner/roles/invitations/delete) по-прежнему используют Organization FOR UPDATE.
Разные проекты не блокируют друг друга общей эксклюзивной блокировкой организации.
Проверки гонок и описание протокола: [доска](board-module.md).

## Обновление существующего окружения

Старые миграции не изменены. Сделайте backup и проверьте новую миграцию на копии.
Этот релиз требует согласованного обновления API: старый writer не передаёт
roleName, старый reader ожидает обязательный roleId. Для текущего одиночного
Compose остановите API на время миграции, затем запустите новый образ:

```sh
docker compose build api migrate
docker compose stop api
docker compose run --rm migrate
docker compose up -d --no-deps --wait api
```

Если миграция завершилась ошибкой, новый API не запускать; сначала выяснить причину.
Возврат к старому API после удаления ролей с отвязкой истории не поддерживается
без отдельной обратной совместимости. Релиз не обещает rolling deployment без
перерыва. PostgreSQL/Redis и их volumes остаются на месте.

После обновления требуется повторный вход: старые ключи Redis не читаются и
исчезнут по TTL. Это не удаляет аккаунты. Пользовательские секреты не меняются.
Для нового окружения env:init создаёт только отсутствующий .env с правами 0600;
существующий файл никогда не перезаписывает.

## Проверки

- Unit: ошибки регистрации, запоздавший login, очистка старой версии пароля,
  конфигурация прокси, редактирование DTO и безопасный формат ошибок.
- HTTP с подменёнными хранилищами: доверенный/недоверенный proxy, лимиты user/IP,
  существующие cookie/Origin/DTO/Swagger-контракты.
- test:tooling: уникальность локальных секретов, права .env и запрет перезаписи.
- test:domain: отдельные PostgreSQL/Redis с runtime/migrator-ролями; миграция
  заполненной старой схемы, повторный deploy, drift, реальные запросы модулей,
  удаление роли после разных состояний приглашения, частичная регистрация,
  управляемая гонка смены пароля и нового входа, токены/TTL/ротация и общий limiter.
- При DOMAIN_API_IMAGE / DOMAIN_MIGRATION_IMAGE test:domain дополнительно
  запускает migration/runtime образы в собственной сети, проверяет healthcheck,
  защиту маршрута и Swagger. Рабочая инфраструктура не используется.

GitHub workflow выполняет эти шаги на push/PR. Сам файл workflow не доказывает,
что удалённый CI прошёл: первый GitHub run появится после публикации изменений.
