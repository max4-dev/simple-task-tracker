# Модуль организаций

Модуль подключён в AppModule, API описан в Swagger `/docs`.
Prisma-схема и применённые миграции не менялись.

## Текущие правила

Роли обозначают специализацию: Frontend, Backend, Designer и т. п.
Они не ограничивают возможности. Все участники организации могут менять её
название/slug, создавать и редактировать роли, назначать роли, приглашать и исключать
других участников. Платформенная роль ADMIN не открывает чужие организации.

Исключения для owner:

- Owner ровно один. Создатель становится им в транзакции вместе с созданием организации.
- Только owner передаёт владение существующему участнику или удаляет организацию.
- Нельзя исключить owner, изменить его системную роль или выйти из организации до передачи владения.
- После передачи у бывшего owner сохраняется его обычная роль; если её не было, роль остаётся null.
- Системная роль owner имеет id=null и isSystem=true. Она не является записью каталога и не редактируется.

Доступ к проекту требует отдельного ProjectMember. Внутри проекта у всех его
участников равные возможности; название роли может отличаться от организационной.
Owner сохраняет полный доступ ко всем проектам организации.
Ранее добавленные массивы permission и project overrides в БД сохранены как задел,
но API их не использует и не принимает в DTO. В профиле коллеги проекты также
проверяются по членству, а не по этим массивам.

## Организации

- `POST /organizations`: name (1–100 символов), slug (3–64, строчные латинские буквы/цифры и одиночные дефисы). Создаётся также пустая визуальная роль Member.
- `GET /organizations`: только свои организации.
- `GET /organizations/:organizationId`: организация и myRole текущего пользователя.
- `PATCH /organizations/:organizationId`: name и/или slug.
- `POST /organizations/:organizationId/leave`: выйти; owner сначала передаёт владение.
- `POST /organizations/:organizationId/transfer-ownership`: body `{ userId }`, только owner.
- `DELETE /organizations/:organizationId`: body `{ password }`, только owner. Безвозвратно удаляются проекты, задачи, роли, приглашения и членства этой организации; аккаунты пользователей и другие организации остаются. Ошибочный пароль не меняет данные. Маршрут ограничен 5 запросами в минуту на IP.

ID — UUID v4. Свои организации/участники/роли/приглашения перечисляются с
`limit=20` (1–100) и `after=<last ID>`. Ответ: items и nextCursor; null означает конец.
Сортировка по ID обеспечивает стабильную последовательность, но не хронологию.

Чужая и отсутствующая организация одинаково возвращают 404. Для участника,
пытающегося выполнить owner-действие, возвращается 403. Ошибки входных полей — 400,
конфликт slug, имени роли или используемой записи — 409. Удаление/выход — 204.

## Участники и роли

- `GET /organizations/:organizationId/members`: участники, имя, email, аватар, роль.
- `PATCH /organizations/:organizationId/members/:userId/role`: body `{ roleId }`; null убирает визуальную роль, не ограничивая действия.
- `DELETE /organizations/:organizationId/members/:userId`: исключить участника, кроме owner.
- `GET /organizations/:organizationId/roles`: items обычных ролей + отдельная systemRole owner.
- `POST /organizations/:organizationId/roles`: name (1–80), необязательное description (до 500).
- `PATCH /organizations/:organizationId/roles/:roleId`: name/description; null очищает описание.
- `DELETE /organizations/:organizationId/roles/:roleId`: только неиспользуемая роль.

Названия ролей уникальны внутри организации без учёта регистра. Имя owner зарезервировано.
Нельзя подставить роль другой организации. Используемая роль не удаляется: сначала
нужно переназначить её у участников/проектов. Связанные приглашения, включая историю,
также удерживают роль; автоматическое удаление истории не выполняется.

Выход или исключение удаляет проектные членства и назначения на задачи этой организации.
Открытые приглашения на email ушедшего участника и приглашения, выпущенные им,
отзываются, чтобы старые ссылки не позволяли обойти исключение.

## Приглашения без почтового сервиса

- `POST /organizations/:organizationId/invitations`: email и roleId. Возвращает invitationUrl один раз.
- `GET /organizations/:organizationId/invitations`: история без токенов и секретных ссылок.
- `DELETE /organizations/:organizationId/invitations/:invitationId`: отозвать ещё не принятое приглашение.
- `POST /organization-invitations/accept`: body `{ token }`, действующая cookie-сессия с указанным email.

Ссылка ведёт на простую backend-страницу с кнопкой принятия:
`/organization-invitations/accept#token=...`. Она требует входа в нужный аккаунт;
пока frontend-форма входа не подключена, можно войти через API/Swagger того же домена.
Принятие не выполняется простым открытием ссылки: нужен явный POST.
Токен находится во фрагменте URL, не отправляется с GET и не попадает в access log.
Страница защищена CSP и Referrer-Policy; ответы организаций не кешируются.

Токен — 32 криптографически случайных байта; в БД только SHA-256. Срок — 7 дней.
Приглашение одноразовое. Параллельные принятия дают ровно одно членство и один успех.
Чужой email — 403; неизвестный/истёкший/отозванный/использованный токен — 400.
Уже существующее членство не меняет роль при повторном приглашении.

Для повторной отправки активную ссылку сначала отзывают. Истёкшая ссылка автоматически
отзывается при создании замены. Принятое приглашение не отзывается: используйте
исключение участника. Добавление в организацию не добавляет в проекты автоматически.

Отправки почты и проверки владения почтой пока нет: email сопоставляется с аккаунтом
согласно текущему development-сценарию. Перед публичным запуском нужен email verification.

## Конфигурация и согласованность

`PUBLIC_API_URL` — публичный origin API, по умолчанию `http://localhost:3001`.
Для своего домена/порта задайте его явно, в production используйте HTTPS.
Он используется в ссылках и добавляется к TRUSTED_ORIGINS, чтобы работала кнопка принятия.
Frontend-origin по-прежнему задаётся через TRUSTED_ORIGINS. Cookies/Origin-защита общие с auth.

Изменения организации сначала блокируют её строку в транзакции, затем читают
текущее членство/owner и выполняют операцию. Это касается ролей, приглашений,
исключения, выхода, передачи и удаления. В будущем проектные операции, меняющие
связанные членства и роли, должны использовать тот же порядок блокировок.
Читающие составные запросы используют RepeatableRead.

## Проверки

`npm test -- --runInBand`: DTO, пагинация, owner, проектная видимость по членству.
`npm run test:e2e -- --runInBand`: общие guards, валидация, cookie, Origin, Swagger с заменёнными хранилищами.
`npm run test:domain`: настоящий HTTP-сервер и временные PostgreSQL/Redis, проверка
чужих организаций и ролей, owner-инвариантов, передачи, удаления по паролю,
приглашений, пагинации, каскадов и конкурентных запросов.
