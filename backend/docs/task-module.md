# Модуль задач

Базовый маршрут: `/organizations/:organizationId/projects/:projectId/tasks`.
Swagger доступен в `/docs`. Вход через существующую HttpOnly cookie; изменяющие
запросы должны передавать разрешённый `Origin`. Ответы имеют `Cache-Control: no-store`.

## Доступ

Читать и изменять задачи могут явные участники проекта и owner организации.
Членство только в организации не даёт доступа к чужому проекту. Роли остаются
визуальными специализациями. Для назначения на задачу даже owner должен иметь
явное членство в проекте. Недоступные проект/задача/статус/тег/участник дают 404.

Архивный проект доступен для чтения, но все команды задач запрещены (409),
включая восстановление задачи. Архивная задача доступна для чтения и истории;
изменять её поля/назначения можно после восстановления. Удаление участника
организации или выход из проекта всё равно очищает назначения в архивных задачах.

## HTTP

- `POST /` — создать задачу; 201, полная карточка.
- `GET /` — список без Markdown-тел; 200, `{ items, nextCursor }`.
- `GET /:taskId` — полная карточка с Markdown; 200.
- `PATCH /:taskId` — изменить поля; 200, полная карточка.
- `PUT /:taskId/assignments` — заменить полный набор назначений; 200, карточка.
- `POST /:taskId/archive` и `POST /:taskId/restore` — 200, карточка.
- `GET /:taskId/history` — минимальная история; 200, `{ items, nextCursor }`.

Безвозвратного удаления задачи пока нет. Доска и перемещение относительно
соседей реализованы: [контракт доски](board-module.md). Уведомления о назначениях:
[NotificationModule](notification-module.md). Файлы/preview, доставка почты и GitHub —
отдельные этапы.
Смена статуса уже поддерживается через PATCH; поле position не принимается от клиента.

Создание:

```json
{
  "title": "Добавить поиск задач",
  "description": "## Требования\nПоиск по названию",
  "statusId": "00000000-0000-4000-8000-000000000001",
  "tagId": null,
  "dueAt": "2026-12-01T18:00:00+03:00",
  "assignments": [
    { "userId": "00000000-0000-4000-8000-000000000002", "kind": "ASSIGNEE" }
  ]
}
```

`title` обязателен, обрезается по краям, 1–200 символов. `description` — сырой Markdown,
до 50 000 символов, по умолчанию пустая строка. Сервер не загружает ссылки/картинки;
будущий клиент должен безопасно рендерить Markdown. Статус по умолчанию — первый
BACKLOG по `(position, id)`, а если таких нет — первый статус проекта. Если статусов
нет, создание возвращает 409. `tagId` и `dueAt` можно очистить через `null`;
остальные поля не принимают null. Дата требует ISO 8601 с явным часовым поясом.

У задачи может быть несколько назначений `RESPONSIBLE`, `ASSIGNEE`, `REVIEWER`;
один участник может совмещать несколько видов. Максимум 100 пар на задачу, одинаковые
пары запрещены. Пустой массив в PUT снимает все назначения. Опущенные поля PATCH
сохраняются; `description: ""` очищает Markdown.

UUID — технический ID. PostgreSQL атомарно выдаёт номер в рамках проекта.
`key` вычисляется как `taskPrefix-number` (например `WEB-3`), `suggestedBranch` —
`branchPrefix/key` (например `feat/WEB-3`) или null без тега. Номера, проект,
создатель, версия и position не задаются клиентом. Подсказка ветки отражает текущие
настройки тега; изменение названия/префикса тега само по себе не является правкой задачи.

## Версии и транзакции

Каждая команда существующей задачи требует `expectedRevision` — целое число
из последнего ответа. Например: `PATCH /:taskId` с
`{ "expectedRevision": 3, "title": "Новое название" }`.

Новая задача имеет revision 1. Реальное изменение увеличивает её ровно на 1 и
записывает событие в той же транзакции. Несовпадение возвращает 409 с кодом
`TASK_REVISION_CONFLICT`; клиент должен перечитать карточку и согласовать изменения.
Запрос с актуальной версией и уже установленными значениями ничего не меняет:
нет новой версии/события/updatedAt. Порядок назначений не имеет значения.
Повтор успешной команды со старой версией возвращает 409, а не создаёт второе событие.

Ошибки полей, недоступные связанные записи и сбой записи события откатывают всю
операцию. После отката создания счётчик номера также откатывается.

Удаление статуса с переносом задач и удаление/выход участника проекта или
организации повышают версии затронутых задач и записывают события. Массовые
изменения выполняются SQL-запросом в текущей транзакции; каскадное удаление
назначений не должно обходить этот путь в будущих сервисах.

Используется существующий порядок блокировок: организация → проект → задача.
Проектные операции берут общую SHARE-блокировку организации и эксклюзивную
блокировку проекта. Разные проекты работают параллельно; изменения членства/owner
организации берут эксклюзивную блокировку организации и синхронизируются с ними. Прямые SQL-изменения Task/TaskAssignment в обход сервисов
не создают историю автоматически.

## Фильтры и пагинация

Список принимает `statusId`, `tagId`, `memberId`, `assignmentKind`, `q` и
`archive=active|archived|all` (по умолчанию active). Фильтры соединяются через AND.
`memberId` вместе с `assignmentKind` относится к одной паре назначения. `q` —
буквальная подстрока названия без учёта регистра; `%`, `_`, `\` не являются масками.
Фильтры по чужим ID дают пустой список и не раскрывают существование этих записей.

`limit` — 1–100 (20 по умолчанию), `after` — номер последней задачи. Сортировка по
возрастанию number; `nextCursor` — число либо null. При переходе на следующую страницу
передавайте те же фильтры. Это не снимок всего списка: между запросами задачи могут
менять состояние. История использует тот же формат, но `after`/`nextCursor` — revision.

## История и миграция

`TaskEvent` хранит revision, actorId, время, вид события и минимальный JSON:
названия изменённых полей, старый/новый ID статуса или тега, добавленные/снятые пары
назначений. Полные версии Markdown и личные контакты в историю не копируются.
Это журнал изменений. События назначения теперь также атомарно создают задания
доставки: [NotificationModule](notification-module.md). События доступны только
при текущем доступе к проекту и удаляются каскадно вместе с задачей/проектом.

Миграция `20261119010000_task_history` добавляет revision и TaskEvent. Существующие
задачи получают revision 1; события задним числом не создаются. Ограничения БД
защищают положительную версию и уникальность `(taskId, revision)` события.

Перед запуском нового API примените миграции штатным migrator через `prisma migrate deploy`.
Не запускайте одновременно старую и новую версию API: старые операции удаления
статуса/участника ещё не записывают историю и не повышают revision.

## Проверки

`npm test -- --runInBand` проверяет DTO, ограничения и сравнение назначений.
`npm run test:domain` поднимает собственные PostgreSQL/Redis без рабочих volumes и
проверяет реальные HTTP-запросы: доступ, валидацию, сохранение/очистку полей,
конфликты версий, конкурентную нумерацию, фильтры, архив, историю, очистку назначений,
массовую смену статуса и откат при искусственном SQL-отказе записи события.
Также проверяются обновление заполненной старой БД, повтор миграций и отсутствие
расхождений Prisma. Рабочие .env, БД и контейнеры при этом не изменяются.

Доска выделена в самостоятельный BoardModule. TaskModule не импортирует его;
общие проверки задач и запись истории доступны через экспортируемый TaskMutationService.
