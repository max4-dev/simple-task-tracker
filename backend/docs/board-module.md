# Доска проекта

Доска — отдельный BoardModule (`src/modules/board`). Он отвечает за выдачу колонок,
порядок карточек, перемещения и перестановку колонок. Новая таблица Board не нужна. HTTP использует обычную HttpOnly cookie,
Origin-защиту и no-store. Доступ имеют явные участники проекта и owner организации.
В архивном проекте разрешено чтение, но все изменения возвращают 409.

## Получение доски

Базовый путь: `/organizations/:organizationId/projects/:projectId`.

- `GET /board` возвращает `{ boardRevision, totalColumns, columns, nextColumnCursor }`.
  Колонка содержит существующие поля статуса и `cards` с `items`, `total`,
  `nextCursor`, `boardRevision`. Пустые колонки сохраняются в ответе.
- `GET /board/columns/:statusId/tasks` возвращает страницу карточек одной колонки:
  `{ boardRevision, total, items, nextCursor }`.

`GET /board` принимает `columnLimit` (1–50, по умолчанию 20), `cardLimit` (1–50,
по умолчанию 10), `afterColumn`. Продолжение колонки принимает `limit` (1–50,
по умолчанию 10), `after`. Таким образом, ни одна выдача не загружает весь проект.
`totalColumns` — число колонок проекта, `cards.total` — число совпавших активных задач
до применения курсора. Колонки упорядочены по `(position, id)`, карточки — также
по `(position, id)`. В карточках нет полного Markdown.

Общие фильтры: `tagId`, `memberId`, `assignmentKind`, `q`. Они работают как в списке
задач; `q` — буквальная подстрока заголовка без учёта регистра. Фильтры только
скрывают карточки, не меняют их позиции. Архивные задачи на доске не выдаются.

Передавайте курсор без изменений вместе с прежними фильтрами. Курсор привязан к
проекту, колонке, фильтрам и версии доски. Неподходящий/повреждённый курсор даёт 400.
Если после предыдущей страницы данные изменились, ответ — 409 с `code: BOARD_CHANGED`.
Клиент должен загрузить доску заново; нельзя продолжать старую страницу, иначе
перемещение карточек могло бы привести к пропускам или дублям. Каждый ответ строится
в едином RepeatableRead-снимке БД. Курсор — позиция чтения, не разрешение доступа.

`boardRevision` — версия представления, а не число пользовательских действий.
SQL-триггеры увеличивают её при изменениях Task, TaskAssignment, TaskStatus, TaskTag,
в том числе при массовом переносе и перебалансировке. Одна команда может увеличить
её несколько раз. Задачные no-op команды, не выполняющие SQL-запись, версию не меняют.
Версия консервативна: изменение Markdown тоже требует перезагрузки следующей страницы.

## Перемещение карточки

`POST /tasks/:taskId/move` возвращает 200 и `{ task, boardRevision }`.

```json
{
  "expectedRevision": 3,
  "statusId": "00000000-0000-4000-8000-000000000001",
  "previousTaskId": "00000000-0000-4000-8000-000000000002",
  "nextTaskId": null
}
```

`expectedRevision` — последняя версия перемещаемой задачи. `previousTaskId` и
`nextTaskId` обязательны; null обозначает начало/конец колонки. Оба null допустимы
только если в целевой колонке нет других активных карточек. Указываются непосредственные
соседи в полном порядке колонки, исключая перемещаемую карточку. Соседи должны быть
активными задачами того же проекта и целевого статуса. Сама задача не может быть соседом.

При активных фильтрах нельзя считать видимые карточки непосредственными соседями:
между ними могут находиться скрытые задачи. Для drag-and-drop клиент должен получить
полный порядок нужного участка без фильтров либо отключить перетаскивание при фильтрации.
Загрузка всей колонки не обязательна: достаточно актуальных соседних карточек.

Старое `expectedRevision` возвращает 409 `TASK_REVISION_CONFLICT`. Изменившийся промежуток
между существующими соседями возвращает 409 `BOARD_CHANGED`. Отсутствующий, архивный или
чужой сосед — 404. Одинаковые/ссылающиеся на себя соседи — 400. Перемещение архивной
задачи — 409. Порядок проверяется после получения блокировки проекта.

Позицию вычисляет сервер с точностью Numeric(30,15), в JSON она всегда строка,
например `1536.000000000000000`. Не преобразовывайте её в JavaScript Number для
сохранения или сортировки: используйте порядок массива. Клиент не задаёт position.
Если промежуток исчерпан, сервер в той же транзакции перенумеровывает активные позиции
колонки с шагом 1024. Относительный порядок сохраняется; revision соседних карточек и
их updatedAt не меняются, boardRevision инвалидирует старые курсоры.

Успешное перемещение увеличивает revision задачи на 1 и добавляет одно событие MOVED:
исходный/новый статус и ID соседей. Уже установленный порядок — no-op. Ошибка события
откатывает перемещение, перебалансировку и версию доски целиком.

## Остальные операции и порядок

Создание задачи, восстановление из архива и смена статуса через PATCH добавляют её
в конец активной колонки. Архивирование убирает карточку из доски. Удаление статуса
с `replacementStatusId` добавляет его задачи после задач целевой колонки, сохраняя
относительный порядок обеих групп. Архивные задачи тоже переносятся; при будущем
восстановлении они будут добавлены в конец активной колонки. Номера задач сохраняются.
Перенесённые задачи получают новую revision и STATUS_REPLACED; перенумерация существующих
позиций целевой колонки сама по себе не считается пользовательской правкой задачи.

## Порядок колонок

`PUT /board/columns/order` принимает:

```json
{
  "expectedBoardRevision": 12,
  "statusIds": [
    "00000000-0000-4000-8000-000000000001",
    "00000000-0000-4000-8000-000000000002"
  ]
}
```

Передайте полный список колонок проекта, включая пустые, ровно по одному разу.
Изменённая версия или неполный/чужой набор — 409 BOARD_CHANGED; дубли — 400.
Ответ: `{ boardRevision, statusIds }`. Порядок обновляется одним SQL-запросом внутри
транзакции. Уже установленный порядок не создаёт SQL-изменений. Создание статуса
ограничено 1000 колонками на проект, полный список reorder имеет тот же предел.

`PATCH /statuses/:statusId` теперь меняет только name/category/color; position
больше не принимается. Создание статуса сохраняет необязательный position, по
умолчанию добавляет колонку после последней. Для перестановки используйте новый маршрут.

## Блокировки, миграция и проверки

Проектные изменения: Organization FOR SHARE → Project FOR UPDATE → повторная
проверка доступа → запись. Разные проекты одной организации могут меняться параллельно.
Внутри одного проекта операции сериализованы. Изменения самой организации, включая
member/owner/roles/delete, сохраняют Organization FOR UPDATE и ждут проектных операций.
Это не снятие проверки членства: после ожидания читается актуальное состояние.

Миграция `20261119020000_board_order` добавляет boardRevision, MOVED, индекс порядка
карточек и SQL-инвалидацию страниц. Старые позиции нормализуются в прежнем порядке
position+id; номера, revision и история существующих задач сохраняются. Исходные
миграции не изменены. Применяйте новую миграцию штатным migrator перед новым API;
старые и новые writers одновременно не запускать: старые версии не знают append/move.

Проверки: точные 30-значные позиции и DTO/cursors в unit-тестах; настоящие HTTP/SQL
сценарии в `npm run test:domain`: страницы, фильтры, устаревшие курсоры, переносы,
исчерпание промежутков/границ числового типа, откат SQL-отказа после перебалансировки,
гонки двух moves, move/delete-status, move/remove-member, ожидание archive и
независимые запросы другого проекта при удерживаемой блокировке первого. Это проверка
протокола конкурентности, не заявление о нагрузочной ёмкости production.

Механика проверена по официальной документации PostgreSQL:
[строковые блокировки](https://www.postgresql.org/docs/18/explicit-locking.html),
[statement triggers и transition tables](https://www.postgresql.org/docs/18/sql-createtrigger.html).

## Границы модулей

AppModule подключает BoardModule и TaskModule. BoardModule импортирует TaskModule
для экспортируемого TaskMutationService; обратной зависимости нет. Контроллеры,
сервис, DTO, курсоры и тесты доски находятся в `src/modules/board`.

TaskModule отвечает за содержимое задач, назначения, архив и историю. Общий
TaskMutationService загружает задачу в границах проекта, проверяет revision/архив
и записывает события. Оба сценария используют тот же transaction client, который
передаёт ProjectAccessService: изменение карточки, история и outbox остаются атомарны.
Правила расчёта позиций в common/database/task-order переиспользуются созданием,
восстановлением и перемещением, без обратного импорта BoardModule.

Перемещение `POST /tasks/:taskId/move` обслуживает BoardController. Путь сохранён
для совместимости API и не определяет принадлежность контроллера к модулю.
Рефакторинг границ модулей не меняет схему БД и не требует новой миграции.
